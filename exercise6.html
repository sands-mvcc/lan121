Hand Out the Addresses, Answer the Names

DHCP and DNS are the two services every network stands on — one leases identities, the other resolves them. In this exercise you'll prove both directions of mastery: first the operations (the DORA exchange, its ports and broadcasts, and what an APIPA address confesses), then the design (carve a real scope for a /24 with static servers, exclusions, and options), then the build — a router-style DHCP simulator where you create the pool and watch a client actually lease an address, and a DNS zone builder where you create A, AAAA, CNAME, MX, and PTR records and run live lookups that walk your own alias chain. Finish with a troubleshooting gauntlet, grade the whole exercise, and download your PDF summary for the LMS.

🎯

Learning Objectives

  1. Explain DHCP operations — the DORA sequence, its ports and broadcast behavior, and lease renewal timing. BLOOM: UNDERSTAND
  2. Design a DHCP scope for a real subnet: exclusion ranges, leasable range, and the gateway and DNS options clients receive. BLOOM: CREATE
  3. Configure a DHCP pool with exclusions, network, default-router, and DNS options using router-style commands, and verify a client lease. BLOOM: APPLY
  4. Match DNS record types — A, AAAA, CNAME, MX, PTR — to the jobs they perform. BLOOM: UNDERSTAND
  5. Create a working DNS zone — address records, an alias chain, mail routing, and reverse lookup — and validate it with queries. BLOOM: CREATE
  6. Diagnose DHCP and DNS failures from their symptoms: APIPA, name-vs-IP reachability splits, rogue servers, and bad scope options. BLOOM: ANALYZE

Graded Tasks

4 PTSNOT GRADED
1.1 What is the correct order of the DHCP lease exchange?
Answer: D-O-R-A. The client asks the room (Discover), a server proposes (Offer), the client accepts publicly (Request), and the server seals it (Ack) with the address, gateway, DNS, and lease time.
1.2 Which two DORA messages does the CLIENT send as broadcasts?
Answer: The client owns no address yet, so its messages (Discover, Request) go to 255.255.255.255. The broadcast Request also politely tells any OTHER offering servers they weren't chosen.
1.3 Which UDP ports does DHCP use?
Answer: UDP 67 (server) / 68 (client) — one of the port pairs the exam expects cold. 53 is DNS; 123 is NTP.
1.4 A workstation shows the address 169.254.31.7. What does that tell you?
Answer: 169.254.x.x is APIPA, the self-assigned fallback. It's not the problem — it's the SYMPTOM that says "investigate DHCP: server down, scope exhausted, or missing relay."

4 PTSNOT GRADED
6.1 Every client on VLAN 30 has a 169.254.x.x address. The only DHCP server lives on VLAN 10 and is healthy. Most likely fix?
Answer: Discover is a broadcast, and routers don't forward broadcasts. Whole-subnet APIPA with a healthy remote server is the relay-is-missing signature — ip helper-address converts the broadcast to unicast.
6.2 A host can ping 8.8.8.8 but ping www.google.com fails with "could not find host." Which layer of service failed?
Answer: Reaching 8.8.8.8 proves addressing, gateway, and routing all work. Only the name lookup fails — the four-ping ladder broke on its last rung. nslookup/dig shows what the resolver returns.
6.3 After a visitor plugged a home router into a wall jack, some clients received leases with a wrong gateway and lost internet access. What happened?
Answer: A rogue server races the real one; whoever Offers first wins the client. Wrong-gateway leases appearing after new hardware = rogue DHCP. DHCP snooping (Lesson 7's Layer 2 defenses) permits Offers only from trusted ports.
6.4 You created a new A record an hour ago, but remote users still reach the OLD address. Local tests against your authoritative server return the new one. Why?
Answer: Every resolver that answered a query before your change caches the old answer for the record's TTL. That's why admins lower the TTL BEFORE a planned migration — and why "it works here but not there" right after a DNS change is usually just time.
